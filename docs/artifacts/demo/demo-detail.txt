  1.4 — the policy config itself (brief line 154: "a minimal policy config
        expressing one RLS rule and one column mask"). config/policies.yaml,
        which is what §2 below turns on. Printed rather than described: the
        ask is to see the config, not only its effect.
--------------------------------------------------------------------------------
  | # The minimal policy config the brief asks for (line 154): one RLS rule and one
  | # column mask, shipped as YAML in the repo exactly as design-doc §6.2/§8.2
  | # promises. Loaded into `policies` by scripts/seed.py.
  | #
  | # The RLS predicate is stored as a JSONB **AST**, never as a SQL string
  | # (ADR-008). A policy that is a string of SQL can only be applied by
  | # concatenating it into a query, which is both an injection surface and
  | # impossible to analyse; an AST can be compiled into the plan, pushed down to a
  | # source, and re-applied authoritatively by the engine.
  | #
  | # `:user` is a parameter, bound at query time from the caller's `sub` claim. It
  | # is never interpolated as text.
  | 
  | policies:
  |   # --- RLS: a support user sees only the issues assigned to them -------------
  |   # This is the rule the 3 -> 1 demo turns on. alice sees 3 rows, bob 1, carol 0.
  |   - policy_id: rls-jira-assignee
  |     tenant_id: tenant_acme
  |     connector_type: jira
  |     resource: issues
  |     kind: RLS
  |     applies_to: support          # matches a SCIM `roles` entry on the token
  |     effect: allow
  |     enabled: true
  |     version: 1
  |     predicate:
  |       op: eq
  |       col: assignee
  |       value: ":user"
  | 
  |   # --- CLS: the reporter's email is masked, never returned raw --------------
  |   # `hash` rather than `drop` deliberately: the column still appears in the
  |   # result with a stable value, so a caller can group by it without ever
  |   # learning the address. Dropping it would change the result shape and make
  |   # the mask invisible in the UI — the Phase 3 spec needs it visible.
  |   - policy_id: cls-jira-reporter
  |     tenant_id: tenant_acme
  |     connector_type: jira
  |     resource: issues
  |     kind: CLS
  |     applies_to: support
  |     effect: allow
  |     enabled: true
  |     version: 1
  |     column_name: reporter_email
  |     mask: hash
  | 
  |   # --- DENY: an explicit deny, which overrides any matching allow --------------
  |   # Two things this fixture exists to prove, and neither is provable without it:
  |   #
  |   #   1. `ENTITLEMENT_DENIED` is REACHABLE. It is one of the six codes the design
  |   #      doc publishes (§8.1); a declared code no seeded state can produce is a
  |   #      claim, not a feature.
  |   #   2. deny-overrides is real. Give a token BOTH `support` (which the allow
  |   #      above matches) and `auditor` (which this matches) and the result must be
  |   #      403, not the allow winning.
  |   #
  |   # `kind: RLS` with `effect: deny` and NO predicate reads as "deny every row of
  |   # this resource". A predicate here would mean "deny these rows", which is a
  |   # different and much subtler feature that nothing in the brief asks for (LAW 5).
  |   #
  |   # Scoped to a role no persona holds by default, so the canonical alice/bob/carol
  |   # demo is completely untouched. The tests mint their own `auditor` token.
  |   - policy_id: deny-jira-issues-auditor
  |     tenant_id: tenant_acme
  |     connector_type: jira
  |     resource: issues
  |     kind: RLS
  |     applies_to: auditor
  |     effect: deny
  |     enabled: true
  |     version: 1
  | 
  |   # There is deliberately NO fixture for default-deny: default-deny is the
  |   # ABSENCE of a matching allow, so seeding one would defeat the point. A token
  |   # with a role no policy names (`contractor`) exercises it — `jira.issues` is a
  |   # GOVERNED resource (the two policies above exist for it), no allow matches
  |   # that role, so it yields EMPTY: 200 with `rows: []`, not 403 and not open.
  |   #
  |   # The distinction that makes this coherent rather than arbitrary: a resource's
  |   # ACCESS is default-deny at the grant (`tenant_connector` -> CONNECTOR_NOT_ENABLED,
  |   # layer L3 in gateway/deps.py). Policies refine rows and columns WITHIN an
  |   # already-granted resource (layer L4). So "no policy rows at all" means
  |   # "granted, unrestricted" — which is why `github.pull_requests`, which no policy
  |   # names, is readable by everyone the tenant has granted GitHub to.

  2.3 / 2.5 / 2.6 are THE TRICHOTOMY. Three different reasons you get no
  rows, which are unremarkable apart and are the sharpest thing in the
  system side by side:
     2.3  entitled, nothing matches   -> 200, rows: []
     2.5  explicitly denied           -> 403 ENTITLEMENT_DENIED
     2.6  no matching allow           -> 200, rows: [] (default-deny)
  A system that collapses these into one answer cannot tell a caller
  whether to ask someone for access or to change their query.
